Cross Word01
The problem

Intent arrives whole.
Facet navigation breaks it into pieces.

A shopper lands with a complete thought — “I need a formal shirt for a wedding, size M, cotton, under ₹2,000.” Traditional search makes them disassemble it into a category tree, four filter panes and a price slider, then reassemble the result themselves.

Every filter is a chance to pick the wrong combination and see zero results. That's the discovery gap — and it's where the funnel leaks.

System architecture

One pipeline, four destinations.

Voice or text enters, gets normalised into English and enriched with session context, then a single intent router sends it down exactly one of four lanes. Everything returns through a grounded synthesis step that can only speak about SKUs the retriever actually returned.

Architecture03
The intent router

Four lanes, one classification.

A single LLM pass emits a typed contract — intent plus extracted slots — that every downstream tool validates against. Nothing runs on free text alone, which is why the assistant behaves like an agent loop instead of a chatbot.

Lane 01 · Search

Find it

Slots (category, price, size, colour, exclusions) become hard filters; the residual phrase goes to hybrid retrieval. Hard constraints are enforced in the query, not hoped for in the ranking.

Lane 02 · Cart

Add it

Resolves “add the second one” against the exact result payload held in session state, then writes to a session-scoped cart. Quantity, removal and cart review are the same tool.

Lane 03 · Compare

Weigh it

Takes two references — ordinal, name, or cart position — and returns a spec-by-spec diff rather than prose, so the difference is readable at a glance.

Lane 04 · Constraint

Solve it

“Kit out my desk for ₹15,000.” N objects under one shared budget — a combinatorial problem, not a retrieval one. Gets its own solver.

Intent routing04
Deep dive · the constraint agent

N objects. One budget. Best possible basket.

“I need a keyboard, a mouse and a monitor, all under ₹15,000 total.” No single vector query answers this — the answer is a combination, and the constraint only exists across items.

1

Decompose. Split the request into N independent object queries, each carrying the shared context (use case, brand preference, quality floor).

2

Fan out. Each sub-query runs through the ordinary search pipeline — same retriever, same filters, same grounding. No parallel code path to maintain.

3

Optimise. Take the top-k candidates per slot and search the combination space for the basket that maximises total relevance subject to Σ price ≤ X.

4

Explain. Return the basket with its total, the headroom left, and the trade-off made — “spent more on the monitor because your top two mice were within ₹200.”

Constraint solving05
Retrieval

A graph and a vector index, doing different jobs.

Dense vectors are good at “something for a beach wedding” and bad at “not white.” Structured filters are the reverse. We run both, and let a knowledge graph carry the relationships neither one holds.

Qdrant

Semantic recall

Sentence-transformer embeddings over the catalog, filtered at query time by the slots the router extracted — so price and size are guarantees, not suggestions.

LightRAG

Relational recall

An entity–relation graph over products, brands and attributes. Answers the questions a flat index can't: what goes with what, what's a sub-brand of what.

BM25

Lexical anchor

Exact model numbers and brand strings that embeddings blur together stay retrievable.

Guardrail

SKU grounding

Synthesis can only reference IDs present in the retrieved set. Measured hallucination rate: 0 / 322.

Retrieval stack06
Supporting agents

The parts that make it feel like a conversation.

Translation

Speak any of them

Language detection ahead of the router, with normalisation to English for retrieval and the reply rendered back in the user's language. Hindi, Hinglish and regional input hit the same pipeline as English — no duplicated index.

Query enhancement

Fix it before it fails

Spelling repair, synonym and vernacular expansion (chappal → sandals), and implicit-slot recovery from history — the size stated three turns ago is still in force.

Session state

Remember the results

The exact result payload of each turn is retained, so ordinals (“the second one”), pronouns (“that one”) and refinements (“cheaper”) resolve against what the user actually saw.

Follow-ups

Offer the next move

Every reply ships two or three concrete next queries drawn from the result set's own attribute spread, so the user never faces an empty prompt.

Clarification

Ask, but only once

When a query is under-specified past a confidence floor, the agent asks one targeted question instead of guessing and returning noise.

Contracts

Typed all the way down

Pydantic contracts sit between every layer. A malformed tool call fails loudly at the boundary rather than silently producing a plausible wrong answer.

Agent roster07
Multilinguality

India doesn't shop in one language.

Shoppers switch scripts mid-sentence — “sasta wala dikhao, under 2000”. We normalise at the edge so the catalog, the index and every downstream agent stay monolingual, and only the first and last hop know a second language exists.

Primary · Gemma

Handles it in-house

Gemma covers detection and translation for the Indic languages we tested, including Hinglish and romanised Hindi, which off-the-shelf translators tend to mangle into nonsense. Running it in the same serving stack as the rest of the pipeline means one deployment, no extra network hop, no per-call cost.

Fallback · Sarvam

Defaults out when it should

When detection confidence is low, or the language falls outside Gemma's strong set, the translation agent defers to Sarvam — built specifically for Indic languages. The swap is a config change behind the same typed contract; nothing downstream can tell which one answered.

  • Transliteration, not just translation. Romanised input is mapped to intent, not translated word-for-word.
  • Brand and model strings are pinned before translation, so boAt never becomes “boat”.
  • Reply is rendered back in the user's original language; product titles stay canonical.
  • Zero index duplication — one English catalog serves every language.

Where it breaks

Five known failure modes — and the fix for each.

None of these are architectural. Every one is a bounded change inside a layer that already exists, which is the point of keeping the layers separate.

Failure 01 · Negation

“…but not in white”

Dense retrieval scores white running shoes as highly relevant. If the parser misses exclude_colors, they dominate the top 3.

Fix: negation is a slot, not a semantic problem. Add exclusion fields to the extraction schema and enforce them as a post-fusion boolean filter — the filter stage already exists.

Failure 02 · Ordinals

“Compare the 2nd and 3rd”

Intent routes correctly, but ordinal indices drift when the result payload updates mid-session — the source of our one Tier 1 exception.

Fix: freeze each turn's results under an immutable turn ID and resolve ordinals against that snapshot, never against live state.

Failure 03 · Open intent

“Something for a Goa wedding”

With no extractable slots, results ride on embeddings alone and can mix tuxedos with swimwear.

Fix: an offline occasion-tagging pass over the catalog, plus one clarifying question when slot confidence falls below threshold.

Failure 04 · Graph depth

Multi-hop relations

We downsample the LightRAG index to hold latency. Pruned edges cost us multi-hop paths — compatible accessories, parent-brand lookups.

Fix: route strictly relational queries to a deterministic lookup table instead of the graph. Faster and more correct than a bigger index.

Failure 05 · Latency

12–14s per turn

Serial LLM hops — translate, enhance, route, synthesise — dominate the budget.

Fix: collapse translation and enhancement into the router call, cache embeddings for repeat slots, and stream synthesis. Roughly a 2× cut with no design change.

Why this is tractable

The layers hold

Four of five fixes land inside a single component behind a typed contract. Nothing above requires rethinking the router, the retriever, or the agent loop — which is what we'd argue makes the design production-shaped rather than demo-shaped.
